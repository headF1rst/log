    🇺🇸 영어로 읽기

    브라운필드 코드베이스에서 AI 코딩 에이전트를 사용하다 보면 기대에 미치지 못하는 결과를 마주하곤 합니다. 작은 수정이나 단발성 작업은 빠르게 처리하지만, 기능이 커지거나 여러 모듈을 넘나드는 요구사항이 들어오면 잘못된 방향으로 흐르기 쉽습니다. 심지어 AI가 생성한 코드를 수정하느라 더 많은 시간이 소요될 때도 있곤 합니다.

    그린필드에서는 잘 동작하던 AI가 브라운필드에서 제대로 작동하지 않는 이유는 바로 컨텍스트 팽창 문제(context bloat problem) 때문입니다. 이번 포스트에서는 컨텍스트 윈도우의 한계가 브라운필드에서 어떻게 저품질 코드로 이어지는지 살펴보고, 컨텍스트를 효과적으로 관리하는 방법을 소개해 보도록 하겠습니다.

    토큰과 컨텍스트 윈도우

    브라운필드에서의 컨텍스트 문제를 이야기하기 전에, 먼저 모델이 입력을 어떻게 처리하는지 살펴보겠습니다.

    AI 코딩 에이전트가 코드를 생성할 때, 사용자가 입력한 프롬프트, 관련 파일의 코드, 프로젝트 구조, 문서 등 모든 정보가 모델에 전달됩니다. 이렇게 전달된 텍스트는 신경망이 처리할 수 있는 토큰 시퀀스로 변환되어야 합니다. 신경망은 유한한 기호 집합으로 이루어진 1차원 시퀀스를 입력으로 받기 때문에, 텍스트를 적절한 크기의 토큰으로 분할하는 토큰화(tokenization) 과정이 필요합니다.

    텍스트를 비트로 변환하면 0과 1 두 기호로만 이루어진 1차원 시퀀스가 생깁니다. 예를 들어 |Viewing이라는 문자열에서 첫 번째 문자인 '|'는 8개의 비트(01111100)로 변환됩니다.

    비트로 이루어진 시퀀스는 길이가 너무 길고 기호 수가 적습니다. 시퀀스 길이는 신경망에서 유한하고 귀중한 자원이기 때문에, 기호가 많고 시퀀스가 짧을수록 효율적입니다. 따라서 시퀀스를 줄이기 위해 비트를 바이트로 변환합니다. 바이트로 변환하면 가능한 기호의 수는 256개(2^8)가 되며, 시퀀스 길이는 8배 짧아집니다.

    여기서 BPE(Byte Pair Encoding) 기법을 사용하면 시퀀스를 더 줄일 수 있습니다. BPE는 자주 연속되는 바이트 쌍을 병합하여 새로운 기호로 만드는 방법으로, 시퀀스 길이를 줄이고 어휘 크기를 늘립니다. 예를 들어 아래와 같이 116 뒤에 32가 오는 패턴이 자주 발생한다면, 이 쌍을 새 기호로 그룹화할 수 있습니다.

    새로운 기호 ID 256을 만들고 모든 (116, 32) 쌍을 대체하면 시퀀스는 짧아지고 어휘는 커집니다. 이 과정을 원하는 만큼 반복할 수 있으며, LLM은 이러한 방식으로 약 100,000개의 어휘를 생성합니다 (GPT-5는 약 200,000개의 토큰을 사용합니다).

    대부분의 토크나이저는 영어 중심으로 학습되어 있습니다. BPE 알고리즘은 학습 데이터에서 자주 나타나는 바이트 패턴을 병합하는데, 영어 텍스트가 훈련 데이터의 대부분을 차지하므로 영어 단어와 서브워드가 단일 토큰으로 많이 등록됩니다. 반면 한국어는 상대적으로 적은 훈련 데이터로 인해 어휘에 충분히 포함되지 못하고, 결과적으로 한 단어가 여러 토큰으로 쪼개집니다.

    하지만 모델이 발전하면서 다국어 토큰화의 불균형도 줄어들고 있습니다. GPT-4에서 사용되던 토크나이저 모델인 cl100k_base의 경우 위의 한국어 문장에 11 토큰을 사용하지만, GPT-5에 사용되는 o200k_base는 영어와 동일하게 7 토큰만 사용합니다.

    컨텍스트 윈도우란 신경망에 입력되는 토큰 시퀀스로, 0개부터 모델이 설정한 최대 크기까지 가변적인 길이를 가질 수 있습니다. 예를 들어 컨텍스트 윈도우 크기가 4일 경우, 4개의 토큰으로 이루어진 시퀀스가 신경망의 입력으로 주어집니다. 토큰 시퀀스가 입력으로 들어오면 신경망은 다음에 올 토큰에 대한 확률 분포를 출력하고, 컨텍스트를 바탕으로 다음에 올 토큰을 예측합니다.

    모델은 훈련 과정에서 정답 토큰의 확률을 높이는 방향으로 파라미터를 점진적으로 조정하며, 이를 통해 문맥을 이해하고 적절한 다음 토큰을 생성할 수 있게 됩니다.

    Dumb Zone

    LLM의 신경망이 다음에 올 토큰을 예측할 때, 현재 컨텍스트 윈도우에 들어 있는 토큰을 기반으로 결정을 내립니다. 문제는 컨텍스트가 커지면서 핵심 정보가 희석되고, 탐색 로그, MCP 호출 로그, 수정 diff 추적 등 노이즈가 급격히 늘어난다는 점입니다.

    따라서 어느 임계점을 넘으면 길어진 컨텍스트로 인해 모델이 올바른 다음 스텝을 선택할 확률이 떨어지게 됩니다. HumanLayer의 Dexter Horthy는 한 컨퍼런스에서 이를 'Dumb Zone'이라고 언급하며, 경험적으로 모델 최대 컨텍스트의 40% 지점부터 태스크에 따라 품질이 떨어지기 시작하는 구간이 온다고 말합니다. (https://youtu.be/rmvDxxNubIg?t=363)

    실제로 한 논문의 벤치마크 결과를 살펴보면 GPT5의 입력 컨텍스트 윈도우 사이즈는 272K이지만 품질에 대한 지표는 32K 지점부터 급격하게 하락하는걸 볼 수 있습니다.

    (Recursive Language Models - https://arxiv.org/pdf/2512.24601)

    • S-NIAH (Single Needle-In-A-Haystack)
      • 관련 없는 텍스트 속에서 특정 구절이나 숫자를 찾는 기본적인 검색 태스크. 입력 길이와 무관하게 찾을 정보는 1개로 고정(O(1) 복잡도)되어 있다.
    • OOLONG (Out Of Lengthy cONtext, Generating)
      • 입력의 거의 모든 라인을 의미론적으로 분석하고 집계해야 하는 태스크. 단순 키워드 검색이 아닌 실제 추론이 필요하며 O(n) 복잡도로 정보 밀도가 매우 높다.
    • OOLONG-Pairs
      • 데이터 항목들의 모든 쌍을 고려해야 하는 태스크. n개 항목에서 n(n-1)/2개의 쌍을 검사해야 하므로 O(n²) 복잡도를 가진다.

    때문에 브라운필드 코드베이스 처럼 탐색해야 하는 코드의 양이 많으면서 복잡한 테스크를 AI로 하여금 잘 수행하게 하기 위해서는, 'Dumb Zone'에 빠지지 않도록 필요한 정보만 선별하여 컨텍스트 윈도우 내에 담아야 합니다.

    컨텍스트를 효율적으로 관리하는 방법

    1. Subagent

    Subagent는 이러한 컨텍스트 관리 문제를 해결하기 위한 효과적인 방법 중 하나입니다. Subagent는 특정 작업을 독립적으로 수행하고 최종 결과만 메인 에이전트에 전달합니다. 예를 들어, 메인 에이전트가 복잡한 멀티스텝 작업을 Subagent에 위임하면 중간 도구 호출로 인한 컨텍스트 팽창 없이 간결한 결과만 받을 수 있습니다.

    각 Subagent는 고유한 시스템 프롬프트, 도구 접근 권한, 독립적인 컨텍스트 윈도우를 가지며, 메인 에이전트와 별개로 여러 subagent를 병렬로 실행할 수 있습니다

    기획자 subagent, QA subagent처럼 특정 역할을 부여하는 방식으로 활용되는 경우도 있지만, Subagent는 본래 컨텍스트 팽창 문제를 해결하기 위해 등장한 개념입니다. 따라서 컨텍스트가 효율적으로 관리될 수 있도록 Subagent를 설계하는 것이 중요합니다.

    즉, Subagent는 탐색 비용을 별도 컨텍스트로 격리하고 부모 컨텍스트에는 결론만 남기는 용도로 활용할 수 있습니다. 예를 들어, 한 번에 대량의 컨텍스트가 필요한 검색,분석,요약 작업은 Glob / Grep / Read 도구 호출을 통해 Subagent의 독립된 컨텍스트 내에서 처리한 뒤, 그 결과만 부모 컨텍스트로 전달하는 방식을 사용할 수 있습니다.

    다음은 코드를 분석하는데 전문화된 code-analyzer subagent의 md 파일입니다.

    codebase-analyzer subagent 
    ---
name: codebase-analyzer
description: 코드베이스 구현 세부사항을 분석합니다. 특정 컴포넌트에 대한 상세 정보가 필요할 때 codebase-analyzer 에이전트를 호출하세요. 항상 그렇듯, 요청 프롬프트가 상세할수록 더 좋은 결과를 얻을 수 있습니다 :)
tools: Read, Grep, Glob, LS
model: sonnet
---

코드가 **어떻게** 동작하는지를 이해하는 전문가입니다. 구현 세부사항을 분석하고, 데이터 흐름을 추적하며, 정확한 `파일:라인` 참조와 함께 기술적 동작 방식을 설명하는 것이 당신의 역할입니다.

## 핵심 원칙: 현재 코드베이스를 있는 그대로 문서화하고 설명하는 것이 유일한 임무

- 사용자가 명시적으로 요청하지 않는 한 개선이나 변경을 제안하지 마세요
- 사용자가 명시적으로 요청하지 않는 한 근본 원인 분석을 수행하지 마세요
- 사용자가 명시적으로 요청하지 않는 한 향후 개선을 제안하지 마세요
- 구현을 비판하거나 "문제점"을 지적하지 마세요
- 코드 품질, 성능 이슈, 보안 우려에 대해 언급하지 마세요
- 리팩토링, 최적화, 더 나은 접근법을 제안하지 마세요
- 오직 무엇이 존재하는지, 어떻게 동작하는지, 컴포넌트 간 어떻게 상호작용하는지만 설명하세요

## 핵심 역할

### 1. 구현 세부사항 분석

- 특정 파일을 읽고 로직 파악
- 핵심 함수와 그 목적 식별
- 메서드 호출 및 데이터 변환 추적
- 중요한 알고리즘이나 패턴 기록

### 2. 데이터 흐름 추적

- 진입점에서 종료점까지 데이터 추적
- 변환 및 검증 매핑
- 상태 변경과 부수 효과 식별
- 컴포넌트 간 API 계약 문서화

### 3. 아키텍처 패턴 식별

- 사용 중인 디자인 패턴 인식
- 아키텍처 결정 사항 기록
- 규칙과 관례 식별
- 시스템 간 통합 지점 파악

## 분석 전략

### 1단계: 진입점 파악

- 요청에 언급된 주요 파일부터 읽기
- export, public 메서드, 라우트 핸들러 확인
- 컴포넌트의 "외부 인터페이스" 식별

### 2단계: 코드 경로 추적

- 함수 호출을 단계별로 추적
- 흐름에 관련된 각 파일을 읽기
- 데이터가 변환되는 지점 기록
- 외부 의존성 식별
- 모든 구성 요소가 어떻게 연결되고 상호작용하는지 깊이 사고하는 시간을 가질 것

### 3단계: 핵심 로직 문서화

- 비즈니스 로직을 있는 그대로 문서화
- 검증, 변환, 에러 처리 설명
- 복잡한 알고리즘이나 계산 설명
- 사용 중인 설정값이나 피처 플래그 기록
- 로직이 올바른지 또는 최적인지 평가하지 말 것
- 잠재적 버그나 문제점을 지적하지 말 것

## 중요 지침

- **모든 주장에 `파일:라인` 참조를 반드시 포함**
- **설명하기 전에 파일을 충분히 읽을 것** - 추측하지 말 것
- **실제 코드 경로를 추적할 것** - 가정하지 말 것
- **"어떻게"에 집중** - "무엇을" 또는 "왜"가 아닌
- **함수명과 변수명을 정확하게** 기재
- **정확한 변환 내용을** 전후 상태와 함께 기록

## 절대 금지 사항

- 구현을 추측하지 말 것
- 에러 처리나 엣지 케이스를 생략하지 말 것
- 설정이나 의존성을 무시하지 말 것
- 아키텍처 권장 사항을 제시하지 말 것
- 코드 품질 분석이나 개선 제안을 하지 말 것
- 버그, 이슈, 잠재적 문제를 지적하지 말 것
- 성능이나 효율성에 대해 언급하지 말 것
- 대안적 구현을 제안하지 말 것
- 디자인 패턴이나 아키텍처 선택을 비판하지 말 것
- 근본 원인 분석을 수행하지 말 것
- 보안 함의를 평가하지 말 것
- 모범 사례나 개선 사항을 권장하지 말 것

## 기억할 것: 당신은 문서 작성자이지, 비평가나 컨설턴트가 아닙니다

당신의 유일한 목적은 현재 코드가 어떻게 동작하는지를, 정밀한 정확도와 정확한 참조로 설명하는 것입니다. 당신은 코드 리뷰나 컨설팅이 아닌, 기존 구현의 기술 문서를 작성하고 있습니다.

시스템을 이해해야 하는 사람을 위해 기존 시스템을 문서화하는 기술 문서 작성자라고 생각하세요. 시스템을 평가하거나 개선하는 엔지니어가 아닙니다. 어떠한 판단이나 변경 제안 없이, 현재 구현을 있는 그대로 이해할 수 있도록 돕는 것이 목표입니다.

    개인적으로는 과거에 프롬프트를 영어로 작성했지만, 요즘은 주로 한국어로 씁니다. 앞서 살펴봤듯 모델의 토크나이저가 발전하면서 다국어 토큰화의 불균형이 많이 줄어들었고, 프롬프트도 결국 유지보수 대상이라고 생각하기 때문에 한국어로 작성하는 편을 택했습니다.

    이 밖에도 웹 검색, 내부 문서 탐색·분석 등 다양한 범용 subagent를 관리하고 있습니다. 여기에 더해, 위 범용 에이전트들을 재사용하면서 TMS 도메인에 특화된 에이전트(플래너·구현·리뷰·테스트 작성)와, 이들을 하나의 워크플로우로 엮는 오케스트레이터 스킬, 그리고 프로젝트 규칙을 문서로 코드화한 정책(policy)까지 한곳에서 관리합니다.

    에이전트는 "누가"를, 스킬은 "어떻게"를, 정책은 "무엇을 지켜야 하는가"를 담당하도록 분리한 것이 핵심입니다. 이렇게 분리해 두면 규칙을 프롬프트에 매번 녹이지 않아도 되고, 새 세션에서도 동일한 규율이 자동으로 적용됩니다.

    2. 오케스트레이션 파이프라인 (RPI → 6단계)

    서브에이전트로 탐색 컨텍스트를 격리할 수 있다면, 다음 단계는 이를 워크플로우 전체에 녹여내는 것입니다. 저는 HumanLayer가 소개한 RPI(Research → Plan → Implement) 워크플로우를 뼈대로 삼되, 프로젝트에 맞게 6단계로 분화시키고 구현 구간을 자동 반복 루프로 감싼 오케스트레이터를 사용합니다.

    RPI의 핵심 아이디어 — 각 단계마다 의도적으로 컨텍스트를 압축해 전체 사용량을 40~60%로 유지하고 Dumb Zone을 피한다 — 는 그대로 계승합니다. 다만 순진한 선형 RPI에는 세 가지 아쉬움이 있었습니다. 매 단계마다 사람이 붙어 있어야 하고, 구현 중 컴파일·테스트가 깨지면 사람이 로그를 읽어 다음 프롬프트를 짜야 하며, 프로젝트 규칙을 매번 프롬프트로 다시 설명해야 한다는 점입니다.

    그래서 저는 RPI를 다음과 같이 확장했습니다. 사람이 개입하는 지점은 정확히 두 곳 — 플랜 승인과 PR 승인 — 이고, 그 사이는 전부 자동으로 흘러갑니다.

    Stage 0  Pre-flight   변경 유형 분류
Stage 1  Explore      병렬 탐색 (codebase-* × N + wiki-lookup + module-impact)
Stage 2  Plan         심층 인터뷰 8문항 → 플랜 문서     ★ 게이트 #1 (플랜 승인)
Stage 3  Decompose    Task DAG (병렬 가능 단위로 분해)
Stage 4+5 Impl+Verify  ┌─ Ralph Loop (MAX_ITER=5) ──────────────┐
                       │  구현 → 컴파일 → 테스트 → 리뷰          │
                       │  실패 시 피드백 담아 재시도             │
                       │  3연속 동일 실패 → Branch Hunt          │
                       └────────────────────────────────────────┘
Stage 6  Record       ADR 자산화                        ★ 게이트 #2 (PR 승인)

    Stage 0 · 1 — Pre-flight & Explore

    먼저 요구사항이나 현재 diff를 보고 변경 유형(스키마 변경인지, API 변경인지, 컨슈머 파급이 있는지)을 분류합니다. 그리고 이 판별 결과에 따라 탐색에 몇 개의 서브에이전트를 투입할지를 정합니다.

    영향 수준조건Explore 구성
    Low변경 파일 ≤ 3analyzer 1 + locator 1
    Medium변경 파일 4~10analyzer 2(다른 관점) + locator 1 + pattern-finder 1
    High변경 파일 > 10, 또는 DDD 변경 + DB 마이그레이션 동시analyzer 3 + locator + pattern-finder + wiki-lookup + module-impact

    앞서 소개한 codebase-locator, codebase-analyzer, codebase-pattern-finder를 그대로 재사용합니다. 작은 변경에 에이전트 6개를 띄우는 건 낭비고, 큰 변경에 1개만 띄우면 컨텍스트 품질이 무너집니다. 토큰은 유한한 자원이므로, 예산을 변경 규모에 맞춰 배분하는 규율을 명시적으로 둔 것입니다.

    Stage 2 — Plan (심층 인터뷰)

    플랜 단계는 8개 질문에 전부 답해야 끝납니다. 답이 불완전하면 에이전트가 계속 질문을 생성합니다.

    1. 이 변경이 전파되는 모듈은? (core, admin-api, consumer, batch …)
    2. 트랜잭션 경계는?
    3. ATDD 시나리오 최소 몇 개? 각각의 Given/When/Then은?
    4. 실패 허용 범위는? (재시도 / 보상 트랜잭션 / DLQ)
    5. DB 마이그레이션 필요 여부? 롤백 SQL은?
    6. 외부 시스템 연동이 있는가? (SOMS/TOMS/BTS/KLS)
    7. 영향 받는 기존 테스트는?
    8. 미결정 사항 / 가정은?

    특히 3번, ATDD 시나리오가 이 파이프라인의 척추입니다. 여기서 확정한 Given/When/Then이 나중에 자동 루프의 종료 기준이 되고, 동시에 리뷰어가 읽을 명세가 됩니다. 예전 글에서 강조했듯, 구현 전에 계획을 검토하는 것은 구현된 코드를 검증하는 것보다 훨씬 높은 레버리지를 가집니다. 플랜 문서가 완성되면 여기서 **사람이 승인(게이트 #1)**합니다. 승인하는 순간 사람은 루프 밖으로 나갑니다.

    Stage 3 — Decompose (Task DAG)

    플랜을 병렬 가능한 단위로 쪼갭니다. 별도 파일이 아니라 플랜 문서에 표 하나로 붙입니다.

    | ID | 작업                | 선행 | 산출물 |
|----|--------------------|------|-------|
| T1 | Entity + 마이그레이션 | -   | Entity.java, V260420.1__*.sql |
| T2 | Repository 메서드    | T1  | Repository.java |
| T3 | Application Service | T1  | Service.java |
| T4 | REST Controller     | T3  | Controller.java |
| T6 | Kafka Consumer      | T3  | Consumer.java |

    {T4, T6}처럼 같은 선행에만 의존하는 작업은 병렬 그룹입니다. 다음 단계의 자동 루프는 이 그룹 단위로 진입합니다.

    Stage 4+5 — Implement + Verify (Ralph Loop)

    여기가 순진한 RPI와 가장 크게 갈리는 지점입니다. 예전에는 구현하다 깨지면 제가 로그를 읽고 다음 프롬프트를 짰습니다. 지금은 루프가 스스로 돕니다.

    while iter < MAX_ITER:            # 기본 5회
    구현 (직전 실패 피드백 포함)
    → ./gradlew compileJava       # 실패 시: 로그 담아 재시도
    → ATDD 테스트 작성/갱신
    → ./gradlew test              # 실패 시: 로그 담아 재시도
    → 마이그레이션 정합성 검사 (해당 시)
    → 품질 리뷰                    # Critical/Major 있으면 재시도
    if 완료 조건 전부 통과: return SUCCESS

    if 동일 실패 3연속: Branch Hunt   # 외부 관점 투입
escalate_to_human()               # 루프가 못 풀면 그때 사람

    루프가 언제 멈춰도 되는가는 프롬프트가 아니라 정책 파일(completion-criteria.md)이 정합니다. 하나라도 미충족이면 루프는 계속 돕니다.

    Branch Hunt. 같은 실패가 3번 연속 나오면 — 루프가 국소 최적에 갇혔다는 신호이므로 — 판을 흔듭니다. 컴파일 실패엔 외부 모델(codex)을 붙여 다른 관점을 얻고, 테스트 실패엔 pattern-finder로 유사 성공 사례를 찾고, 도메인 이해 부족이 의심되면 wiki-lookup으로 도메인 정책을 재확인합니다. Branch Hunt는 독립 서브에이전트로 돌아 메인 컨텍스트를 오염시키지 않습니다.

    에스컬레이션. 그래도 안 풀리면(MAX_ITER 도달, 플랜 자체의 모순, 정책 간 충돌 등) 루프를 멈추고 사람을 부릅니다. 이때 "iteration N/5, 마지막 실패 유형, 시도한 해결책, 권장 다음 행동" 형식으로 보고합니다. 사람은 문제를 처음부터 파는 게 아니라, 이미 좁혀진 선택지 앞에서 판단만 합니다.

    completion-criteria.md (Ralph Loop 종료 기준) 
    # Completion Criteria

Ralph Loop가 SUCCESS로 종결될 최소 기준. 하나라도 미충족이면 루프를 계속 돌린다.

## 필수 (모두 충족해야 SUCCESS)
- [ ] :{영향모듈}:compileJava / compileTestJava 성공
- [ ] :{영향모듈}:test 통과
- [ ] ATDD 시나리오 전부 통과 (플랜 `## 완료 조건` 섹션 정의 N개)
- [ ] tms-review severity Critical / Major 0건
- [ ] module-boundaries 위반 0건
- [ ] layered-ddd 위반 0건
- [ ] 마이그레이션 포함 시 db-migration 준수

## 조건부 (해당 시 필수)
### Kafka 컨슈머 변경
- [ ] idempotency 보증 (중복 메시지 처리 안전)
- [ ] 실패 처리 / DLQ 전략 문서화

## Branch Hunt 발동 조건
동일한 실패 signature가 3회 연속 발생하면 Branch Hunt를 삽입한다.
(동일 signature = 예외 클래스 + 발생 위치(파일:라인) + 실패 테스트 이름의 교집합)

    Stage 6 — Record (ADR로 자산화)

    마지막 단계에서는 앞선 단계들의 산출물(검증·탐색·플랜·구현·리뷰 보고서)을 1장짜리 **ADR(Architecture Decision Record)**로 압축합니다. 이 ADR의 독자는 미래의 저도, 아키텍트도 아닌 PR 리뷰어입니다. 리뷰어가 세션에 ADR을 컨텍스트로 얹고 "왜 이 트랜잭션 경계를 택했나"를 대화형으로 물어볼 수 있게 하려는 것입니다.

    솔직히 말하면 이 단계는 아직 자리를 잡아가는 중입니다. Explore→Plan→Implement 구간은 실제 티켓 수십 건으로 검증됐지만, ADR 자산화는 이제 막 쌓기 시작했습니다. 하네스는 완성물이 아니라 매 티켓마다 조금씩 진화하는 시스템입니다.

    3. 정책의 코드화 — 마법은 정책 문서에 있다

    마법 같은 프롬프트는 없습니다. 그렇다면 이 파이프라인의 품질은 어디서 나올까요. 답은 .claude/policies/입니다. 프로젝트 규칙을 프롬프트에 매번 녹이는 대신 외부화된 권위 문서로 못박아 두었습니다. 이 문서들은 "과거 코드나 예시보다 우선한다"고 명시돼 있어서, 저장소에 낡은 관례가 남아 있어도 에이전트는 정책을 따릅니다.

    특히 리뷰 병목 이야기의 핵심은 review-severity.md입니다. 리뷰어가 머릿속으로 하던 "이게 배포 장애 날 수준인가, 그냥 스타일 문제인가"의 판단을 네 단계로 코드화했습니다.

    review-severity.md 
    ## Critical  배포 장애 가능성 / 데이터 정합성 파손 / 계약 파손 / 계층 위반으로 인한 구조 손상
## Major     기능 누락 가능성 / 테스트 부족으로 인한 회귀 위험 / 영향 모듈 반영 누락
## Minor     패턴 일관성 저하 / 유지보수성 저하
## Suggestion 필수는 아니지만 개선 여지

    완료 조건이 "Critical/Major 0건"을 요구하니, 사람 리뷰어에게 도달하기 전에 기계가 Critical/Major를 이미 다 걸러냅니다. 사람은 Minor와 Suggestion, 그리고 "이 설계 방향이 맞나" 같은 판단에만 집중합니다.

    4. 지식 플라이휠 — llm-wiki

    브라운필드의 컨텍스트 문제는 사실 두 겹입니다. 하나는 코드 컨텍스트(어느 파일이 무엇을 하나), 다른 하나는 도메인 컨텍스트입니다. 배송·물류 도메인에서는 "오배송과 정정배송이 어떻게 다른지", "KLS 배송대행 운송장이 왜 TOMS를 거치지 않는지" 같은 지식이 코드 어디에도 적혀 있지 않습니다. 코드만 읽어선 알 수 없습니다.

    그래서 도메인 지식을 담는 별도의 위키 저장소를 두고, 개발 파이프라인의 Stage 1(Explore)에서 wiki-lookup으로 이 지식을 코드 탐색과 나란히 주입합니다. 반대로 Stage 6(Record)에서 새 도메인 용어나 정책 변경이 감지되면 "위키 업데이트가 필요하다"고 사람에게 알립니다(자동 수정은 하지 않습니다).

    그리고 개발 하네스 안에도 작은 플라이휠이 있습니다. Stage 6가 ADR을 쌓을수록, 미래의 Stage 1이 "과거 유사 작업"으로 그 ADR을 참조해 탐색 품질을 올립니다. 하네스를 굴릴수록 하네스가 똑똑해지는 구조입니다.

    그래도 마법의 프롬프트는 없다

    여기까지 파이프라인을 정교하게 짜면 완벽한 결과물이 나올 것 같지만, 현실은 그렇지 않습니다. 브라운필드 코드베이스는 여러 요구사항이 뒤섞인 로직이 공존하기 때문에, AI가 코드의 의도를 완벽히 이해하기 어렵습니다.

    그렇기 때문에 사람의 개입 지점을 없애는 게 아니라, 판단이 가장 값진 곳에 남겨두는 것이 중요합니다. 각 단계마다 마크다운 문서와 ADR을 생성하도록 한 이유도 여기 있습니다. 코드 리뷰 과정에서 팀원들이 수백, 수천 줄의 코드 대신 문서를 읽으면, 리뷰 부담을 줄이면서도 작업의 맥락을 더 깊이 공유할 수 있습니다. 코드 작성 비용이 줄어 하루에도 수천 줄이 쏟아지는 요즘, 코드 리뷰가 병목이 된 조직이라면 문서를 리뷰 프로세스에 포함하는 것이 현실적인 대안이 됩니다.

    워크플로우가 놓친 것

    익숙하지 않은 코드베이스에서 개발 환경 편의를 위해 배송 상태를 시작 상태까지 한 번에 변경하는 API를 수정한 적이 있습니다. 어느 순간부터 이 API가 제대로 동작하지 않았고, 원인 파악부터 수정까지 파이프라인을 그대로 적용했습니다.

    문제의 원인은 해당 API가 호출하는 서비스 로직의 인터페이스가 다른 API를 수정하는 과정에서 바뀌었는데, 기존 호출 쪽에서 유효하지 않은 인자를 그대로 넘겨주고 있던 것이었습니다. 그런데 워크플로우는 근본 원인을 해결하는 대신, 유효하지 않은 값이 들어올 때 방어하는 로직만 작성했습니다.

    더 큰 문제는 저도 검증 단계에서 이걸 인지하지 못했다는 점입니다. 코드베이스에 여러 요구사항이 뒤섞여 있다 보니, AI도 저도 해당 코드의 본래 의도를 제대로 파악하지 못한 채 넘어간 것입니다.

    이 경험은 지금 하네스의 정책에 그대로 박혀 있습니다. completion-criteria는 방어 코드로 증상을 덮는 대신 근본 원인 해결과 ATDD 시나리오 통과를 요구하고, review-severity는 "계층 위반으로 인한 구조 손상"을 Critical로 규정합니다. 하지만 정책도 만능은 아닙니다. 결국 의도가 코드에 명확히 드러나도록 작성하고 리팩토링하는 습관은 AI 시대에도 여전히 유효합니다. AI는 코드에 적혀 있는 것을 읽을 뿐, 작성자의 머릿속에 있는 의도까지 읽지는 못합니다. 코드가 의도를 숨기고 있다면, 파이프라인이 아무리 정교해도 엉뚱한 방향으로 흐를 수 있습니다.

    마무리

    RPI를 뼈대로 6단계 파이프라인을 짜고, 구현 구간을 Ralph Loop로 감싸고, 규칙을 정책으로 코드화하면서, 저는 사람을 워크플로우에서 빼낸 것이 아니라 판단이 가장 값진 두 지점으로 옮겼습니다. 방향을 정하는 플랜 승인, 그리고 결과를 검증하는 PR 승인. 그 사이의 컴파일 오류·테스트 실패·국소 최적 함정은 루프가 스스로 처리하고, 못 풀 때만 좁혀진 선택지를 들고 저를 부릅니다.

    파이프라인 덕에 하루에 처리하는 티켓 수는 분명 늘었습니다. 하지만 속도가 빨라진다고 해서 그게 곧 성장으로 이어지는 건 아닌 것 같습니다. 자동화를 정교하게 만들수록, 정작 문제를 깊이 고민하는 시간을 스스로 지켜내야 한다는 걸 더 자주 느낍니다. 두 개의 게이트를 남겨둔 것도 결국 그래서입니다. AI에게 생각마저 위임하지 않도록, 판단해야 할 지점을 의도적으로 남겨두는 것. 그 지점에서만큼은 짧은 주기로 빠르게 질문하고 함께 고민하는 과정을, 저는 여전히 가장 중요하게 여깁니다.
