    병렬 외부 호출, CompletableFuture와 Flux.flatMap 무엇을 쓸까
    2026-05-19
    MSAWebClient
    🇺🇸 영어로 읽기

    지난 글에서 외부 API 호출을 DB 트랜잭션 밖으로 빼고, 여러 건을 Flux.flatMap으로 병렬 통지하도록 코드를 정리했습니다. 그때 "병렬 호출은 CompletableFuture로도 할 수 있다"고 잠깐 언급하고 넘어갔는데, 이번 글에서 두 방식을 본격적으로 비교해 보겠습니다.

    둘 다 "여러 외부 호출을 동시에 띄운다"는 같은 목표를 달성하지만, 그 내부 동작과 적합한 상황은 꽤 다릅니다.

    같은 목표, 다른 코드

    먼저 두 방식이 어떻게 생겼는지 나란히 봅시다.

    CompletableFuture

    public void notifyAll(List<DeliveryStatusCommand> commands) {
    List<CompletableFuture<Void>> futures = commands.stream()
        .map(cmd -> CompletableFuture.runAsync(
            () -> partnerApiClient.notifyStatusBlocking(cmd), executor))
        .toList();

    CompletableFuture.allOf(futures.toArray(new CompletableFuture[0])).join();
}

    Flux.flatMap

    public void notifyAll(List<DeliveryStatusCommand> commands) {
    Flux.fromIterable(commands)
        .flatMap(cmd -> partnerApiClient.notifyStatus(cmd.trackingNo(), cmd.status()))
        .subscribe();
}

    겉보기엔 비슷해 보이지만, 가장 큰 차이는 스레드 모델에 있습니다.

    1. 스레드 모델 — 가장 본질적인 차이

    CompletableFuture: 작업 하나당 스레드 하나

    CompletableFuture.runAsync는 작업을 스레드 풀의 스레드 하나에 할당합니다. 그런데 그 작업이 블로킹 HTTP 호출(notifyStatusBlocking)이라면, 응답을 기다리는 동안 스레드는 블로킹된 채 아무 일도 못 하고 묶여 있습니다.

    100건을 동시에 호출하려면 스레드 풀에 최소 100개의 스레드가 필요하고, 외부 응답이 느려질수록 더 많은 스레드가 점유됩니다. 스레드는 스택 메모리(약 1MB)와 컨텍스트 스위칭 비용을 동반하는 비싼 자원이라, 수천 건 동시 호출에는 한계가 분명합니다.

    Flux.flatMap: 소수의 스레드가 수천 요청을 처리

    flatMap은 각 항목에 대해 논블로킹 호출(Mono)을 동시에 띄우고, 응답을 기다리는 동안 스레드를 점유하지 않습니다. Netty의 이벤트 루프 스레드(보통 CPU 코어 수만큼)가 "응답이 도착한 것부터" 골라 처리합니다. 덕분에 소수의 스레드로 수천 개의 in-flight 요청을 감당할 수 있습니다.

    CompletableFuture (블로킹)          Flux.flatMap (논블로킹)
┌──────────────────────┐           ┌──────────────────────┐
│ Thread-1 → 요청1 대기 │ (놀고있음) │ EventLoop-1          │
│ Thread-2 → 요청2 대기 │ (놀고있음) │  ├ 요청1 (대기중)     │
│ Thread-3 → 요청3 대기 │ (놀고있음) │  ├ 요청2 (대기중)     │
│   ...                │           │  ├ 요청3 (응답옴!처리) │
│ Thread-100 → 요청100 │ (놀고있음) │  └ ... 요청1000       │
└──────────────────────┘           └──────────────────────┘
   스레드 100개 필요                   스레드 몇 개로 충분

    물론 CompletableFuture도 논블로킹 클라이언트와 조합하면 스레드를 덜 점유할 수 있습니다. 핵심은 "블로킹 호출을 CompletableFuture로 감싸는 흔한 패턴"이 스레드를 작업 수만큼 소비한다는 점입니다.

    2. 동시성 제어와 부가 기능

    항목Flux.flatMapCompletableFuture
    동시 실행 개수 제한flatMap(fn, concurrency) 두 번째 인자로 간단히 제어스레드 풀 크기로 간접 제어
    백프레셔(backpressure)내장 지원 — 소비 속도에 맞춰 자동 조절없음 — 직접 큐/세마포어 구현 필요
    재시도/타임아웃.retryWhen(), .timeout() 연산자로 선언적직접 코드로 구현

    예를 들어 "파트너사를 보호하기 위해 최대 10건씩만 동시 호출"은 Reactor에서 한 줄입니다.

    .flatMap(cmd -> partnerApiClient.notifyStatus(cmd), 10) // 동시 10건으로 제한

    CompletableFuture로 같은 제어를 하려면 고정 크기 스레드 풀이나 세마포어를 직접 구성해야 합니다.

    3. 패러다임 정합성 — 현실적인 결정 기준

    이 시리즈의 코드는 이미 WebClient를 쓰고 있고, WebClient는 그 자체가 Reactor(Mono/Flux) 기반입니다.

    • notifyStatus()는 이미 Mono<Void>를 반환합니다.
    • Flux.flatMap을 쓰면 이 Mono를 그대로 자연스럽게 이어붙입니다.
    • 반면 CompletableFuture를 쓰려면 Mono를 .toFuture()로 변환하거나, 애초에 블로킹 클라이언트로 감싸야 합니다. 두 비동기 패러다임을 억지로 잇는 셈이고, 변환 지점마다 예외 전파 누락이나 스레드 누수 같은 버그가 끼어들기 쉽습니다.

    그럼 CompletableFuture는 언제 쓸까

    Flux가 항상 정답은 아닙니다. CompletableFuture가 더 나은 상황도 분명히 있습니다.

    상황추천
    이미 WebClient/Reactor 사용 중Flux.flatMap — 변환 없이 자연스럽고, 동시성·재시도·백프레셔를 선언적으로 처리
    RestTemplate 등 블로킹 클라이언트 + Reactor 도입 부담CompletableFuture — 기존 동기 코드에 점진적으로 비동기 추가
    호출 건수가 적고(수 건) 팀이 Reactor에 익숙하지 않음CompletableFuture — 학습 곡선이 낮고 디버깅이 쉬움

    특히 디버깅 측면에서 차이가 큽니다. Flux는 비동기 흐름이 여러 스레드를 넘나들기 때문에 스택 트레이스가 끊겨 원인 추적이 어렵습니다(checkpoint()나 onOperatorDebug() 같은 보조 수단이 필요합니다). 반면 CompletableFuture는 상대적으로 흐름이 단순해 추적이 쉽습니다.

    정리

    기준CompletableFutureFlux.flatMap
    스레드 모델작업당 스레드 점유소수 이벤트 루프가 다수 처리
    대규모 동시 호출스레드 수에 제약매우 유리
    동시성/재시도/백프레셔직접 구현연산자로 선언적
    블로킹 클라이언트와 궁합좋음변환 필요
    디버깅 난이도낮음높음

    결론적으로 "무엇이 더 빠른가"보다 "이미 쓰는 도구와 같은 패러다임인가"가 핵심 판단 기준입니다. WebClient를 쓰는 이상 Flux로 통일하는 것이 코드 일관성과 유지보수 면에서 유리하고, 동시성 제어·재시도 같은 부가 요구사항도 한 줄로 표현할 수 있습니다. 다만 팀의 Reactor 숙련도와 디버깅 비용도 함께 저울질해야 현실적인 선택을 할 수 있습니다.
