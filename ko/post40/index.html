    코딩 에이전트가 등장한 이후 조직의 가장 큰 관심사는 '생산성이 얼마나 향상되었는가'였습니다. 회사 입장에서 매달 지불하는 AI 구독료만큼 개발자의 생산성이 올라갔는지 확인하고 싶은 것은 당연합니다.

    개개인의 업무 효율은 높아졌을 수 있으나, 프로덕트 관점에서의 생산성은 크게 개선되지 않았습니다. 코드를 생산하는 속도는 분명 빨라졌지만 실질적인 가치가 만들어지는 시점인 배포까지 걸리는 시간은 그대로였기 때문입니다.

    이유는 단순합니다. 프로덕트는 개발만으로 끝나지 않기 때문입니다. 기획, 개발, 리뷰, QA를 거쳐 배포에 이르기까지 거쳐야 하는 단계가 많고, 단계 마다 사람과 일정을 조율하는 시간이 끼어 있습니다. 그래서 개발이 빨라지더라도 전체 리드타임은 여전히 가장 느린 단계에 맞춰지게 됩니다. 배포까지의 시간을 줄이고 싶다면 이미 빨라진 단계가 아니라, 그 때문에 새롭게 드러난 병목을 봐야 합니다.

    저희 팀에서 가장 먼저 드러난 병목은 코드 리뷰였습니다. 이번 포스트에서는 이 병목을 풀기 위해 시도했던 경험들을 정리해 보고자 합니다. 리뷰가 실제로 병목인지 지표로 확인한 과정부터, '리뷰이가 더 좋은 PR을 쓰게 하자'는 시도가 왜 실패했는지, 그리고 관점을 바꾸어 리뷰어를 돕는 슬랙 봇을 만들기까지의 판단과 구현을 함께 살펴보겠습니다.

    1. PR은 늘고 첫 리뷰까지의 대기는 길어졌다

    PR 수와 첫 리뷰 대기 시간 비교

    먼저 리뷰가 정말 병목인지, 아니면 PR이 늘어난 탓에 리뷰가 느려졌다고 느끼는 착시인지 확인하고 싶었습니다. 그래서 레포지토리 하나를 골라 사내에 코딩 에이전트가 도입되기 이전 3개월과 이후 3개월의 지표를 뽑아 비교해 보았습니다.

    지표도입 이전 3개월도입 이후 3개월변화
    주당 PR 수7개15개+114%
    PR 오픈 → 첫 리뷰까지 걸린 시간1.16h6.24h+438%

    각 기간에 진행한 프로젝트의 규모처럼 통제할 수 없는 변수가 있어, 이 숫자를 그대로 신뢰할 수는 없습니다. 하지만 방향성은 분명했습니다. 주당 PR 수는 두 배로 늘었고, 늘어난 PR의 내용을 하나씩 읽고 맥락을 파악하는 데 시간이 걸리면서 첫 리뷰 코멘트가 달리기까지 여섯 배 넘는 시간을 쓰고 있었습니다.

    즉, 코드를 작성하는 속도가 빨라진 만큼 그 뒤의 단계가 밀리고 있었던 것을 확인할 수 있었습니다.

    코드 리뷰를 유지하기로 한 이유

    코딩 에이전트로 인한 리뷰 병목은 우리 팀만의 문제가 아니었기에, 다른 조직들은 이 문제를 어떻게 풀고 있는지 알아보았습니다. 그러다 일부 조직에서는 코드 리뷰 단계 자체를 생략한다는 이야기를 접했습니다. 리뷰로 문제를 걸러내는 대신 AI 검증 루프를 촘촘히 두고, 문제가 생기면 빠르게 롤백한다는 전략이었습니다. 단위 테스트부터 E2E까지 탄탄하게 갖춰져 있고 즉각적인 롤백이 가능한 환경이기에 선택할 수 있는 방식이었을것입니다.

    하지만 코드 리뷰는 단순히 버그를 거르는 행위만이 아닙니다. 리뷰를 통해 팀은 동료가 어떤 문제를 어떤 방식으로 풀었는지 알게 되고, 그 코드가 놓인 도메인의 맥락을 함께 나누게 됩니다.

    리뷰를 생략하면 당장의 병목은 사라질지 몰라도, 코드를 이해하는 사람은 작성자 한 명으로 좁혀집니다. 여러 사람이 함께 코드를 이해하고 있을 때 비로소 "이건 이렇게 하는 게 낫지 않을까" 하는 대화가 오가며, 이를 바탕으로 새로운 아이디어와 또 다른 개발 루프가 탄생할 수 있습니다. AI가 코드를 대신 써주는 시대일수록, 그 코드를 팀이 온전히 이해하고 있는지가 오히려 더 중요하다고 생각했습니다.

    그래서 방향을 '리뷰를 없애자'가 아니라 '리뷰는 유지하면서 리뷰에 드는 시간을 줄이자'로 정리했습니다.

    사람이 리뷰에서 확인해야 할 것

    그렇다면 리뷰에 드는 시간은 어떻게 줄일 수 있을까요. 이 고민은 자연스럽게 '좋은 PR이란 무엇인가'라는 질문으로 이어졌습니다. 작은 단위로 쪼갠 PR, 친절한 작업 배경 설명처럼 흔히 꼽히는 좋은 PR의 조건들을 보면, 결국 리뷰어를 배려하는 데 초점이 맞춰져 있었습니다.

    동시에 지금의 코드 리뷰에서 사람이 감당해야 할 몫이 무엇인지도 다시 짚어보게 되었습니다. 구문 오류나 스타일, 단순 버그 같은 것들은 이미 AI 도구가 사람보다 더 빠르고 정확하게 찾아냅니다. 반면 AI는 작성자가 이 작업을 어떤 의도와 맥락에서 진행했는지는 알지 못합니다. 이 구분을 다음과 같이 정리해 보았습니다.

    코드 리뷰에서 의도 리뷰로. AI가 잡을 수 있는 것(구문, 스타일, 단순 버그, 보안 패턴)은 AI에게 맡기고, 사람은 AI가 잡을 수 없는 것(구현 의도, 아키텍처 맥락, 비즈니스 판단, 팀의 암묵지와 어긋나는 지점)에 집중하는 구조입니다.

    의도를 리뷰하려면 PR에 의도가 온전히 담겨 있어야 하고, 이를 담을 수 있는 사람은 작성자뿐입니다. 결국 리뷰이가 리뷰어를 배려해 스스로 좋은 PR을 작성해야 한다고 판단했고, 자연스럽게 '리뷰이가 PR을 더 잘 쓰도록 돕는 도구'를 고민하기 시작했습니다.

    2. 세 번의 시도 끝에 리뷰어를 돕기로 결정한 과정

    첫 번째 시도: 잘 쓰이지 않은 PR 작성 스킬

    첫 번째 시도는 작업자가 작업 배경과 의도를 description에 잘 담아 PR을 작성할 수 있도록 돕는 스킬이었습니다. Jira 티켓과 관련 Confluence 정책서를 기반으로 작업 배경을 자동으로 작성하고, 시각적인 이해를 돕는 다이어그램까지 함께 생성해주는 /create-pr을 만들어 팀에 공유했습니다.

    결과부터 말하면, 실제로 사용하는 사람은 많지 않았습니다. 이유를 곱씹어 보니 안 써도 그만이었기 때문입니다. description이 부실할 때 불편함을 느끼는 사람은 PR 작성자가 아니라 리뷰어입니다. 리뷰어는 불편하지만, PR을 생성하는 리뷰이는 불편하지 않습니다. 리뷰이의 입장에서는 오히려 PR을 올리기 전에 거쳐야 할 단계가 하나 늘어나는 셈입니다.

    여기서 얻은 첫 번째 배움은, 고통을 느끼는 사람과 행동을 바꿔야 하는 사람이 다르면 그 도구는 사용되지 않는다는 것이었습니다.

    두 번째 시도: ADR이 있어도 번거로운 리뷰 준비

    자발적 사용이 안 되니, 다음은 강제였습니다. 개발 워크플로우의 마지막 단계에 hook을 추가해서, PR을 생성하기 전에 ADR 문서를 자동으로 생성하고 PR에 첨부하는 방식을 구상했습니다. hook이 문서 생성을 강제하므로 누락될 일이 없고, ADR이 PR에 첨부되어 있으면 리뷰어가 Claude Code로 인터랙티브하게 코드 리뷰를 진행할 수 있지 않을까 하는 기대도 있었습니다.

    팀에 이 방식을 공유하자 다음과 같은 피드백이 돌아왔습니다.

    리뷰를 하려면 해당 브랜치를 pull 받아 checkout하고, 클로드코드를 실행해야 한다는 점이 번거로울 것 같다.

    부정하기 어려웠습니다. 터미널을 열고, 브랜치를 받아오고, checkout 하고, Claude Code를 실행하는 그 과정은 만든 사람 입장에서도 귀찮아서 잘 쓰지 않을 것 같았습니다.

    세 번째 시도: 평가로 받아들여진 배려 온도

    세 번째 시도는 AI PR 리마인더였습니다. AI가 리뷰어 한 명당 리뷰해야 할 PR들의 맥락을 조회한 뒤 슬랙으로 발송해주는 방식인데, 여기에 각 PR마다 '배려 온도'라는 표기도 추가했습니다.

    PR description이 얼마나 풍부하게 작성되어 있는지를 기준으로 리뷰어에 대한 배려 정도를 온도로 나타낸 것이었고, description이 부실한 PR에 대해서는 리뷰이에게 멘션으로 PR을 좀 더 보완해달라는 식의 내용을 담았습니다.

    하지만 미처 이 알림을 받을 리뷰이의 기분을 생각하지 못했습니다. 알림의 내용은 리뷰이에게 배려가 부족하다고 통보하는 모양새였습니다. 온도라는 표현으로 부드럽게 감쌌을 뿐, 개인의 태도를 수치로 환산해 통보한다는 사실은 그대로였고, 다소 강요하는 듯한 뉘앙스를 주었습니다. 실제로 기분이 좋지 않았다는 피드백을 받았는데, 받는 쪽에 있었다면 다르지 않았을 것 같습니다. 만들기 전에 받는 사람의 입장을 먼저 헤아렸어야 했습니다.

    여기서 얻은 세 번째 배움은, 사람의 태도를 평가하는 도구는 그 평가가 정확하든 아니든 반발을 살 수밖에 없다는 것이었습니다.

    이 일을 계기로 두 가지를 깨달았습니다. 하나는 다른 사람의 행동을 바꾸려 드는 접근 자체가 잘못된 출발점이었다는 것이었고, 다른 하나는 그동안의 시도가 전부 '리뷰이가 리뷰어를 위해 더 많은 맥락을 제공한다'는 한 가지 관점에 갇혀 있었다는 사실이었습니다.

    리뷰어가 맥락을 파악하도록 돕기

    그래서 리뷰이에게 무언가를 요구하는 대신, 리뷰어가 자신의 리뷰 시간을 스스로 줄일 수 있게 AI가 돕는 방식으로 접근을 바꾸었습니다.

    여러 수정을 거쳐, 지금은 Claude Code remote 스케줄러가 각 PR의 코드, Jira 티켓 내용, 그리고 정책서를 읽어와서 '배경'과 '의도', 관련 문서와 PR을 한눈에 파악할 수 있는 카드를 구성해 리뷰어별로 발송하고 있습니다.

    리뷰이는 아무것도 하지 않아도 됩니다. 리뷰어가 받아보는 정보의 밀도가 올라갔을 뿐입니다. '배려 온도' 시절과 하는 일은 비슷해 보이지만, 사람에게 요구하던 것을 시스템이 대신 수행한다는 점에서 정반대의 설계입니다.

    PR 리마인더 슬랙 메시지PR 맥락 카드 상세

    여기서 한 걸음 더 나아가고 싶었습니다. 카드로 맥락을 확인하는 것을 넘어, 리뷰어가 PR에 대해 AI와 대화하며 검토하는 인터랙티브 리뷰 경험이었습니다. 변경된 함수가 영향을 미치는 지점이나 의도를 그 자리에서 질의하고 즉각 근거 있는 답을 받는 흐름을 목표로 삼았습니다.

    그런데 이 지점에서 두 번째 시도의 실패 원인이 그대로 되살아납니다. hook 방식의 문제는 리뷰를 위해 터미널을 열고, 리뷰할 브랜치를 받아오고, checkout 한 다음, Claude Code를 실행해야 한다는 마찰이었습니다. 그렇다면 이 일련의 과정을 사람이 직접 수행하는 대신 슬랙 봇에게 위임하면 마찰을 없앨 수 있겠다고 판단했습니다. PR 리마인더 스레드에서 봇을 멘션하면, 봇이 해당 브랜치의 worktree를 만들고, 저장소를 통째로 읽어 질문에 답변하는 구조입니다. 리뷰어는 슬랙을 벗어날 필요가 없습니다.

    그렇게 슬랙 봇을 만들기로 했습니다. 하지만 구현에 앞서 먼저 이 봇을 어디에 띄울 것인지를 정해야 했습니다.

    3. 로컬에서 시작하기: Socket Mode를 택한 이유

    앞선 시도들을 통해, 아무리 좋은 아이디어라도 팀에서 실제로 쓰일지는 직접 운영해 봐야 알 수 있다는 점을 배웠습니다. 그래서 처음부터 서버를 마련하기보다 로컬 머신에서 launchd로 봇을 띄워 사용성을 먼저 검증하기로 했습니다.

    PC가 꺼지거나 잠자기에 들어가면 봇이 멈춘다는 명확한 한계가 있었지만, 이를 오히려 전환 기준으로 보았습니다. 봇이 팀의 업무 흐름에 안착해 "봇이 꺼져서 불편하다"는 피드백이 나오는 시점을 서버로 이전할 적기라고 판단했습니다.

    공개 URL이 없는 로컬 머신

    로컬 실행을 위해서는 이벤트 수신 방식을 고려해야 했습니다. Slack의 기본 방식인 Events API는 Slack 서버가 앱의 공개 HTTP 엔드포인트로 웹훅을 쏘는 구조입니다. 하지만 사내망 방화벽 뒤에 있는 로컬 머신에는 외부 요청을 직접 받을 수 있는 공개 URL이 없었습니다.

    외부에서 들어오는 길은 막혀 있지만, 다행히 로컬 머신에서 외부로 나가는 연결은 자유로웠습니다. 외부의 호출을 기다리는 대신 봇이 먼저 Slack에 연결을 맺고 이벤트를 받아오는 Socket Mode가 이 환경에 정확히 들어맞았습니다.

    Socket Mode의 연결과 이벤트 수신

    Socket Mode: 공개 HTTP 엔드포인트 대신, 앱이 먼저 열어둔 WebSocket(WSS) 연결로 Slack 이벤트를 받아오는 방식. 이벤트 페이로드는 웹훅(Events API)과 동일하며 배달 경로만 다릅니다.

    애플리케이션 코드에서는 @slack/bolt의 App에 두 종류의 토큰과 함께 socketMode: true를 넘겨주는 것만으로 시작할 수 있습니다.

    // src/app.ts
const app = new App({
  appToken: cfg.appToken, // xapp-: WebSocket 연결 통로를 열기 위한 App-Level 토큰
  token: cfg.botToken,    // xoxb-: 메시지 게시, 파일 업로드 등 봇 API 호출용 토큰
  socketMode: true,
});

    설정은 단순해 보이지만, 이 한 줄 뒤에서는 세 단계의 프로토콜 계약이 동작합니다.

    1) 연결 수립: 두 토큰과 아웃바운드 WebSocket

    먼저 appToken(xapp-, connections:write 스코프)으로 Slack API를 호출해 일회용 WebSocket URL을 발급받습니다. 봇이 이 URL로 연결을 요청하고 HTTP Upgrade 핸드셰이크를 마치면, 사내망 방화벽의 인바운드 차단을 우회하는 양방향 통로가 열립니다. 이후 실제 슬랙에 메시지를 쓰거나 반응을 달 때는 일반 봇 토큰(xoxb-)을 사용합니다. 즉, 통로를 여는 열쇠(appToken)와 통로 안에서 일하는 신분증(botToken)이 분리되어 있는 구조입니다.

    2) 이벤트 수신과 즉시 확인: envelope과 ack

    연결이 수립되면 Slack은 이벤트를 envelope(봉투) 객체에 담아 내려보냅니다.

    {
  "envelope_id": "1d3c79ab-…",
  "type": "events_api",
  "payload": { /* app_mention 등 실제 이벤트 */ },
  "accepts_response_payload": false
}

    클라이언트는 봉투를 받자마자 {"envelope_id": "…"}를 즉시 회신(ack)해야 합니다. bolt 프레임워크가 핸들러 바깥에서 ack를 자동 처리해 주어 코드에 직접 드러나지는 않지만, "ack가 제시간에 닿지 않으면 Slack은 동일한 이벤트를 다시 전송한다"는 계약은 웹훅과 동일하게 유지됩니다.

    3) 연결 수명: 무중단 갱신(refresh)

    Socket Mode 연결은 영구적이지 않습니다. Slack은 주기적으로 disconnect 메시지(reason: "refresh_requested")를 보내 새 연결로 갈아탈 것을 요구합니다. bolt의 SocketModeClient는 새 WebSocket을 먼저 연결한 뒤 기존 연결을 닫는 방식으로 이벤트를 유실 없이 인계합니다. 봇 로그에 정기적으로 찍히는 재연결 기록은 에러가 아니라 무중단 유지를 위한 정상적인 프로토콜 동작입니다.

    정리하면, Events API와 Socket Mode의 차이는 이렇게 비교할 수 있습니다.

    항목Events API (웹훅)Socket Mode
    연결 방향Slack → 앱 (인바운드)앱 → Slack (아웃바운드, WSS)
    공개 URL / TLS 인증서필수불필요
    수신 확인3초 내 HTTP 200envelope_id ack
    재전송있음 (x-slack-retry-num)있음 (ack 미수신 시)
    수평 확장로드밸런서 뒤에 자유롭게연결 단위라 제약 (동시 연결 수 상한)
    앱 디렉터리 공개 배포가능불가 (내부용 앱 전용)
    적합한 곳클라우드 상시 서비스사내망·로컬 상주 봇

    재전송된 이벤트의 중복 처리

    Slack은 ack을 수신 받지 못하면 이벤트를 재전송 하기 때문에, 멘션 핸들러는 다른 작업에 앞서 이벤트 ID로 중복을 확인하도록 하였습니다.

    // src/router/mentionHandler.ts
if (dedup.seen(context.eventId ?? `${event.ts}`)) return;
if (!isAllowed(cfg, event.user, event.channel)) return;

    중복 확인에는 고정 용량 FIFO를 얹은 Set을 사용합니다. 이벤트의 event_id를 키로 기록하고, 500개를 넘으면 오래된 항목부터 제거해 메모리 사용량을 제한합니다.

    4. PR의 맥락을 읽기 위한 저장소 접근과 격리

    Socket Mode로 멘션을 받을 수 있게 됐지만, 제대로 된 답변을 하려면 PR의 단순 diff뿐 아니라 저장소의 주변 맥락까지 넓게 읽을 수 있어야 합니다. 이때부터는 "코드를 어떤 단위로 체크아웃할 것인가", "에이전트에게 어디까지 도구 권한을 열어줄 것인가"라는 구체적인 샌드박싱 문제가 시작됩니다.

    사용자가 스레드에서 @봇 https://github.com/org/repo/pull/123 이 PR 설명해줘라고 멘션했을 때 실행되는 전체 파이프라인은 다음과 같습니다:

    Slack (클라우드)                      로컬 머신 (봇 프로세스)
┌───────────────────┐                ┌─────────────────────────────────────────┐
│ app_mention 발생   │                │ @slack/bolt (Socket Mode)               │
│   envelope 래핑    │──WSS(아웃바운드)─▶ ack 즉시 회신                          │
│                   │◀───────────────│    │                                    │
└───────────────────┘                │    ▼ mentionHandler                     │
                                     │  ① dedup / isAllowed / parsePrUrl       │
                                     │  ② isRepoAllowed (repo 화이트리스트)      │
                                     │  ③ gh pr view / gh pr diff (PR 수집)     │
                                     │  ④ git worktree add --detach (격리)      │
                                     │  ⑤ Agent SDK query(): 읽기전용 탐색       │
                                     │     └─ PR 리뷰 문서 HTML 생성 (리뷰 스킬)   │

        이후 같은 스레드에서 봇을 다시 멘션하면 ⑥의 세션을 resume해 멀티턴 Q&A

    이 입구 검증을 거친 뒤 실행되는 파이프라인에서는 인증 위임, 코드 격리, 에이전트 권한 제어라는 세 가지 문제를 풀어야 했습니다.

    gh CLI로 PR 데이터 가져오기: 토큰 없는 인증 위임

    PR 메타데이터 수집은 gh CLI 세 번의 호출로 끝납니다.

    // src/features/prReview/prFetcher.ts
const metaJson = await run('gh', [
  'pr', 'view', String(number), '--repo', full,
  '--json', 'title,body,headRefOid,headRefName,files,comments,reviews',
]);
const diff = await run('gh', ['pr', 'diff', String(number), '--repo', full]);
// 인라인 코드 코멘트는 pr view JSON에 없어 별도 REST 호출(실패해도 비치명적 격리)
const inlineJson = await run('gh', ['api', `repos/${full}/pulls/${number}/comments?per_page=100`]);

    octokit 같은 GitHub SDK 대신 CLI를 택한 가장 큰 이유는 인증 위임입니다. 봇이 구동되는 로컬 머신에는 이미 저의 gh 세션이 로그인되어 있고, 토큰 발급·갱신·키체인 저장을 전부 gh가 알아서 관리합니다. REST API 호출마저 gh api를 통하므로 봇 코드에는 GitHub 토큰 관리 로직이 단 한 줄도 필요 없습니다. 부수적으로 gh pr diff가 이미 검증된 unified diff를 바로 돌려주어 diff 파싱 코드를 직접 구현할 필요도 없었습니다.

    worktree로 리뷰별 코드 고정

    diff만 LLM에 넘겨주면 설명의 깊이가 수정된 몇 줄에만 갇히게 됩니다. "이 함수를 왜 바꿨는가"에 제대로 답하려면 변경된 함수를 호출하는 상위 모듈이나 프로젝트의 기존 설계 패턴까지 저장소 전체를 탐색할 수 있어야 합니다.

    따라서 세션마다 독립된 코드 체크아웃이 필수적입니다. 하지만 동시 리뷰가 5건 들어온다고 저장소를 5개씩 통째로 클론한다면 디스크와 네트워크 비용이 걷잡을 수 없이 커집니다.

    git의 worktree가 이 문제를 깔끔하게 해결합니다. 주방(공통 .git 객체 저장소)은 하나만 두고, 도마(작업 트리)만 리뷰마다 가볍게 하나씩 얹는 방식입니다. 객체 저장소를 공유하므로 추가 체크아웃 비용만 발생합니다.

    // src/integrations/worktreeManager.ts
await mutex.run(repoFullName, async () => {
  if (!existsSync(clone)) {
    await run('git', ['clone', `https://github.com/${repoFullName}.git`, clone]);
  }
  await run('git', ['-C', clone, 'fetch', 'origin', '--prune']);
  // 이전 세션의 잔재가 남아있다면 멱등하게 선제거 (self-heal)
  if (existsSync(wt)) { await removeWorktree(clone, wt); }
  await run('git', ['-C', clone, 'worktree', 'add', '--detach', wt, headSha]);
});
    • mutex.run(repoFullName, …): 동일 저장소에 동시 리뷰 요청이 들어오면 여러 git fetch가 .git/index.lock을 두고 충돌합니다. 저장소 단위 파일 락 경합을 방지하기 위해, 저장소별 뮤텍스를 두어 fetch를 직렬화했습니다(서로 다른 저장소는 완전 병렬).
    • --detach로 headSha 고정: 브랜치명이 아니라 커밋 SHA를 고정 체크아웃합니다. 리뷰 도중 작성자가 브랜치에 새 커밋을 push하더라도, 봇이 분석하는 코드는 "결과물을 생성한 바로 그 시점의 코드"로 박제되어 리뷰 문서와 실제 코드의 불일치를 막습니다.
    • self-heal (자가 복구): 봇이 갑자기 재시작되더라도 다음 리뷰가 시작될 때 기존 잔재 경로를 정리하고 새로 띄웁니다. 유휴 worktree를 회수하는 주기적 리퍼(reaper)와 함께 디스크 누수를 원천 차단합니다.

    에이전트의 도구와 파일 접근 제한하기: 프롬프트가 아닌 구조적 차단

    worktree가 준비되면 Claude Agent SDK의 query()를 봇 프로세스 내부에서 직접 실행합니다. 이때 LLM은 저장소를 탐색하는 에이전트가 되는데, 슬랙 멘션이라는 신뢰할 수 없는 외부 입력에 그대로 노출됩니다. "이 저장소 코드를 전부 삭제해줘" 같은 프롬프트 주입 공격을 항상 전제해야 하므로, 보안은 프롬프트로 부탁하는 것이 아니라 런타임 구조로 강제해야 합니다.

    // src/integrations/claudeRunner.ts (발췌)
const opt: QueryOptions = {
  cwd,                                        // 이 리뷰의 worktree 경로
  allowedTools: ['Read', 'Grep', 'Glob', 'Write', 'Agent', 'Task', 'WebSearch', 'WebFetch'],
  disallowedTools: ['Bash'],                  // ← 핵심 방어선 (전역 deny)
  settingSources: ['user'],                   // 스킬 로드용
  strictMcpConfig: true,                      // 외부 .mcp.json 미상속
  permissionMode: 'dontAsk',                  // 허용 목록 밖 도구는 묻지 않고 거부
  // …hooks: PreToolUse 훅으로 Write 경로를 리뷰 산출물 디렉토리로 강제 제한
};

    여기서 실측 과정에서 발견한 중요한 보안 함정이 있었습니다.

    1. Write가 허용된 이유와 경로 가드: 에이전트는 코드리뷰 결과물인 HTML 파일을 로컬에 작성해야 하므로 Write 도구 자체는 허용해야 했습니다. 대신 소스 코드 변조를 막기 위해 PreToolUse 훅을 두어, 쓰기 작업이 worktree 외부의 지정된 산출물 디렉토리 안에서만 일어나도록 경로를 강제했습니다.
    2. 화이트리스트의 허점과 disallowedTools: 처음에는 allowedTools에서 Bash를 빼면 셸 명령이 차단될 것이라 생각했습니다. 하지만 에이전트가 코드 탐색을 위해 Agent 도구로 하위 서브에이전트를 생성할 때, 부모의 allowedTools 제한이 자식 서브에이전트에게는 상속되지 않는 문제가 있었습니다(SDK 기본 동작). 즉, 자식이 기본 권한인 Bash를 들고 실행되면 임의 시스템 명령이 뚫릴 수 있었습니다. 유일한 실효 게이트는 자식 프로세스까지 전역 적용되는 disallowedTools: ['Bash']였습니다.

    5. diff 요약을 넘어 이해를 돕는 리뷰 문서 설계

    스킬로 리뷰 문서의 구성 기준 정하기

    저장소를 안전하게 읽는 파이프라인을 갖춘 뒤에는, 리뷰어에게 어떤 리뷰 문서를 보여줄 것인가가 다음 고민이었습니다. 리뷰어에게 필요한 것은 변경된 코드 줄 자체가 아니라, 기존 시스템이 어떻게 동작하고 있었고 작성자가 왜 이런 방식으로 풀었는가라는 전후 맥락입니다.

    리뷰 문서의 기준을 세우는 데 큰 영감을 준 것은 Geoffrey Litt의 발표 *"Understanding is the new bottleneck"*이었습니다. AI 시대의 병목은 코드 작성이 아니라 코드 이해에 있으며, 좋은 리뷰 문서는 단순 검증을 넘어 '이해'를 도와야 한다는 관점이었습니다.

    이를 바탕으로 봇이 생성할 결과물의 구조를 네 가지 원칙으로 설계했습니다.

    • 배경 먼저 설명하기: "무엇이 바뀌었는가"로 바로 들어가지 않고, 이번 작업을 이해하는 데 필요한 기존 시스템의 동작 원리를 먼저 짚어줍니다.
    • 직관과 의도 우선: 복잡한 코드 diff에 앞서, 작성자가 도달하려는 목표를 한눈에 파악할 수 있는 개요를 먼저 제시합니다.
    • 읽는 순서대로 재배열한 Diff (Literate Diff): Git 파일 알파벳 순서가 아니라, 논리적 흐름 순서로 변경점을 재배열하고 각 블록마다 친절한 산문 설명을 덧붙입니다.
    • 이해 점검용 퀴즈: 문서를 끝까지 스크롤만 하고 넘기지 않도록, 핵심 변경 의도를 제대로 파악했는지 스스로 확인해 볼 수 있는 퀴즈를 문서 말미에 배치합니다.

    지금 봇이 쓰는 explain-diff-html은 이 원칙을 한국어 HTML 산출물과 팀의 리뷰 흐름에 맞게 구현한 스킬입니다. 첫 턴에는 한국어 리뷰 문서 한 장을 만들고, 후속 질문은 같은 슬랙 스레드에서 세션이 답합니다. 스킬 지침에 모아둔 구체적인 품질 기준 일부는 다음과 같습니다.

    - 간극을 메워라: diff를 그대로 재진술하지 말고, 작성자가 "리뷰어도 안다"고 깔고 간 것을 메워라
- 깊이: 코드가 *무엇*을 하는지(L1)에 멈추지 말고, *왜 그렇게 했는지*와 대안 대비 트레이드오프·리스크(L3)까지
- 구체: 주장마다 바로 옆에 구체적 근거(코드 발췌·`파일:라인`·숫자)를 붙여라

    이 기준을 프롬프트에 명시하면서, 단순히 diff를 다시 쓰는 대신 배경과 판단 근거를 설명하도록 유도했습니다.

    6. 후속 질문을 이어가기 위한 세션과 캐시 설계

    리뷰 문서를 받아본 리뷰어는 스레드에서 자연스럽게 후속 질문을 이어갑니다. 하지만 로컬 프로세스는 언제든 재시작될 수 있고, 디스크 공간도 한정되어 있습니다. 대화의 연속성을 보장하면서도 머신의 자원을 고갈시키지 않기 위한 세션과 캐시 구조를 설계해야 했습니다.

    SQLite에 스레드와 세션 연결 정보 저장하기

    같은 스레드에서 후속 질문을 받으려면 Slack의 thread_ts와 Agent SDK의 세션 ID를 매핑해 두어야 합니다. 로컬 봇 하나를 위해 무거운 외부 DB를 띄우기보다, 파일 하나로 끝나면서도 Node.js 22에 내장된 node:sqlite를 선택했습니다.

    // src/core/sessionStore.ts
const { DatabaseSync } = process.getBuiltinModule('node:sqlite') as typeof import('node:sqlite');

export function createSessionStore(dbPath: string) {
  const db = new DatabaseSync(dbPath);
  db.exec('PRAGMA journal_mode = WAL'); // 동시 읽기/쓰기 성능 향상 및 락 충돌 방지

  db.exec(`
    CREATE TABLE IF NOT EXISTS sessions (
      thread_ts     TEXT PRIMARY KEY,   -- Slack 스레드 식별자 (스레드당 1:1 매핑)
      session_id    TEXT,               -- Agent SDK 세션(resume 대상)
      repo          TEXT NOT NULL,
      pr_number     INTEGER NOT NULL,
      worktree_path TEXT NOT NULL,
      last_active   INTEGER NOT NULL,   -- idle 리퍼의 회수 기준
      head_sha      TEXT                -- 검토하던 커밋 SHA
    );
  `);
}

    테이블의 기본 키는 thread_ts입니다. 즉, **"하나의 스레드는 한 번에 하나의 활성 PR 맥락만 추적한다"**는 규칙입니다. 만약 팀원이 같은 스레드에서 다른 PR URL을 새로 멘션하면, 봇은 고아 파일이 남지 않도록 이전 PR의 worktree를 디스크에서 먼저 정리한 뒤 새 PR 정보로 레코드를 갱신(UPSERT)합니다.

    세션이 끊겨도 코드와 스레드에서 복원하기

    정상적인 흐름에서는 SQLite에 기록된 세션 ID로 Agent SDK 대화를 재개합니다. 이때 봇은 후속 멘션이 올 때마다 Slack API(conversations.replies)로 스레드 메시지를 매번 다시 읽어옵니다. SDK 세션 메모리에는 봇과 사용자 간의 질의응답만 남기 때문에, 멘션 사이에 동료들이 스레드에서 자유롭게 나눈 대화 맥락까지 답변에 온전히 반영하기 위함입니다.

    하지만 로컬 머신에서는 유휴 자원 정리를 위해 worktree가 삭제되었거나, 프로세스 재시작으로 메모리 세션이 사라질 수 있습니다. 이때도 봇이 '대화가 끊겼다'며 멈추지 않고, 두 가지 정보만으로 세션을 자가 복구합니다.

    1. 검토하던 코드: DB에 기록된 head_sha로 해당 시점의 worktree를 즉시 다시 체크아웃합니다.
    2. 대화 내용: Slack 스레드의 전체 대화를 다시 긁어와 새 세션의 프롬프트 맥락으로 주입합니다.
    상황감지 방법복원 대응
    worktree가 삭제됨existsSync(rec.worktreePath) 검사head_sha로 worktree를 즉시 재생성하고 세션 재개
    세션 ID가 없음rec.sessionId 부재 확인PR 맥락과 스레드 대화 내용으로 새 세션 시작
    세션 기록이 유실됨SDK resume 에러 감지스레드 히스토리로 대화 맥락을 복원해 새 세션 시작

    산출물 캐시와 동시성 보호

    여러 리뷰어가 같은 PR을 동시에 검토할 때 불필요한 모델 실행과 자원 낭비를 막아야 합니다. 결과물인 HTML 문서는 repo + PR번호 + headSha를 조합한 키로 캐시하고, 동일 대상에 대한 동시 요청은 뮤텍스로 제어하였습니다.

    // src/features/conversation/conversationService.ts
const res = await mutex.run(`${repoFullName}#${prRef.number}@${headSha}`, async () => {
  const cached = artifacts.get(cacheKey);            // 캐시 히트: LLM·worktree 없이 즉시 제공
  if (cached && existsSync(cached.htmlPath)) { /* … */ }
  if (slotStatus({ threadTs, repoFullName, headSha }).full) { /* 자리가 날 때까지 정직한 대기 안내 */ }
  // …생성 경로
});
    1. 캐시 무효화의 자동화: 캐시 키에 커밋 해시(headSha)가 포함되어 있어, 작업자가 브랜치에 새 커밋을 푸시하면 별도의 무효화 로직 없이도 최신 코드로 새 리뷰가 동작합니다.
    2. 동일 대상 중복 실행 방지(Stampede 방지): 두 사용자가 같은 PR을 거의 동시에 멘션하더라도, 뮤텍스를 통해 선행 작업이 끝날 때까지 후행 요청은 대기했다가 방금 생성된 캐시 결과를 즉시 전달받습니다.
    3. 자원 상한 분리: 동시 리뷰 상한(5건)은 실제 모델을 실행하는 생성 경로에서만 카운트합니다. 캐시 히트는 자원을 거의 쓰지 않으므로 상한에 걸리지 않고 즉시 응답합니다.
    4. 성공 경로만 캐싱: 리뷰 문서가 정상 생성되었을 때만 캐시에 기록합니다. 생성 도중 오류가 났을 때 실패 상태가 캐시되어 이후 요청까지 먹통이 되는 결함을 방지합니다.

    마지막으로, 리뷰를 거듭할수록 로컬 디스크가 차오르지 않도록 유휴 worktree는 last_active 타임스탬프를 기준으로 주기적인 리퍼(reaper)가 회수합니다. 캐시와 자동 수거 메커니즘 덕분에, 봇은 한정된 로컬 자원 안에서도 수십 개의 리뷰 세션을 안정적으로 소화할 수 있었습니다.

    현재 이 슬랙 봇은 PR 리뷰뿐만 아니라 배포 프로세스 자동화, 에러 온콜, 로그 분석 등 더 많은 역할을 담당하는 팀의 범용 AI 슬랙 봇으로 자리 잡았습니다. 다만 기능이 늘어난 만큼 사용자 요청이 엉뚱한 작업으로 튀는 '라우팅 오분류'라는 새로운 문제를 마주해야 했는데요. 다음 포스트에서는 이 라우팅 문제를 어떻게 해결했는지 다뤄보도록 하겠습니다.
